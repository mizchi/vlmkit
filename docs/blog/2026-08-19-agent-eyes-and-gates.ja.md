# エージェントには目がある。それでも動くものは見えない

2026-08-19 / vlmkit 0.11.1

vlmkit は「決定論的な静的検査のルールセット」と「それを回す fuzzy な
ワークフロースキル」を、意図的に**両面**で出しています。片方だけでは足りない、
という結論に至るまでの経緯と、それを確かめるために Klondike ソリティアを
1 本書いた話を書きます。

数値はすべてこのリポジトリに記録された実行のものです（2026-08-16〜18、
0.11.1）。出所は各節でファイル名を挙げます。

---

## 1. 前提: 現代のエージェントは目を持っている

数年前まで、コーディングエージェントに「このページ、変じゃない?」と聞くのは
無意味でした。今は違います。スクリーンショットを渡せば、崩れたレイアウトを
指摘してきます。これは検証の前提を変えました。

どのくらい本当に見えているのか。`examples/solitaire/` に対して、
**決定論的ゲートが全部緑のまま、スクリーンショットだけが見つけた欠陥が
4 件**あります。

| 目が見つけた欠陥 | なぜゲートには見えなかったか |
|---|---|
| 4 つのファウンデーションが `♠ ♥ ♦ ♣` を広告しているのに、ルールはどのエースもどの空きスロットに置いていた（標準の Klondike の挙動）。進行した盤面は `♠ ♥ ♦ ♣` のヒントの下に `A♠ A♦ A♥ A♣` を並べていた | マークアップは妥当で、ラベルもあり、到達可能でコントラストも足りていた。**意味**だけが嘘だった |
| 戻るリンクがツールバーの 2 行目に折り返し、タイトルの真下・左端に着地して、迷子のコンテンツに見えた | リンクは存在し、フォーカス可能で、44px 以上、コントラストも通る。どの行にいても全部通る |
| `Deal` ラベルが 1 行目の末尾で終わり、その `<select>` が次の行から始まった | `for` / `id` の関連付けは正しい。a11y ゲートには報告すべきものが無い |
| `Left 52` が、見た目にカードが残っているストックの隣にあって、ストックの残数として読めた（実際はファウンデーションに未到達の枚数）。今は `Foundations 0/52` で増えていく | 文字列は可視でコントラストも足りている。「その数字が何として読まれるか」はどのルールにも書けない |

つまり目は本物の検出器です。「エージェントに見せれば十分では?」という疑問は
半分正しい。

半分しか正しくない理由も、このプロジェクトの歴史そのものです。名前の VLM は
vision-language model のことで、最初は「VLM にページを判定させ、正解データと
突き合わせて精度を測る」ところから始まりました。分かったのは
**判定こそが不安定な部分だった**ということでした。測定が製品になり、VLM 機能は
キー必須のオプションに降格し、名前は化石になりました
（詳細は [`docs/introduce.ja.md`](../introduce.ja.md)）。

目は**発見**に強く、**判定**に弱い。同じページを 2 回見て違う答えを出すものは
CI に置けません。さらに、検査可能なゴールを与えられたエージェントは
ゴールを騙しにきます。実際に記録されている例:

- 必須コピーを `font-size: 0` の span に隠す（`check copy` を通すため）
- アサーションが通る 50ms だけ `aria-disabled` を反転させる（支援技術には
  嘘をついたまま）
- 自作チェックへ静かにフォールバックして「検証済み」と報告する

だから判定側は決定論でなければならない、というのが vlmkit の下半分です。

## 2. 目に原理的に見えないもの: 時間と操作

静止画には、原理的に写らないものが 2 つあります。

**操作**。ソリティアのスクリーンショットは、そのカードが合法な列にドラッグ
できるかを何も語りません。ドロップ先がハイライトされる条件がゲームルールに
依存しているとき、静止画に写っているのは「ハイライトされていない今」だけです。

**時間**。deal 中のフレームは毎回違います。これは理屈ではなく、実際にゲートが
踏みました:

```
verdict: NO DEFECTS, 1 WARN
! [low-contrast-text] …>span @1280: rgb(213,75,97) on rgb(253,253,251) is contrast 4.12:1
```

カードの赤は `#c8102e` で、カード面に対して 5.8:1、通ります。
`rgb(213,75,97)` はその赤が `opacity: 0.2` でフェルトに合成されたもの —
**deal の途中で空中にあるカード**です。セレクタ付きで報告が出るので、読んだ人は
存在しない色バグを探しに行きます。これは人間でもエージェントでも同じで、
「見た瞬間」が結論を変えます。

vlmkit がここで取っている手は 2 つです。

### 時間を消す

`check animation` は、フレームを眺めるのではなく**すべてのアニメーションを
一時停止し、決められたサンプル点にシークして**測ります。各点でピクセルが
実際に動いたか、ページはいつ静止するか、`prefers-reduced-motion` を守るか。
シークするので、実行ごとに同じ答えになります。

そして「ページが静止した」の定義は 1 箇所に集約されています（`settlePage`、
`tests/settle-page-single-definition.test.mjs` がそれを強制）。
network idle → `fonts.ready` → `document.getAnimations()` の **finite な
アニメーションの完了待ち**。無限アニメーション（スピナー）は待たずに除外し、
待ち時間には上限（既定 2 秒）を置いています。前者が無いと 1 つのスピナーが
全ゲートを固め、後者が無いと 30 秒のイントロが実行を止めます。
上の偽陽性はこれで消えました（`?animate=0` 無しで `verdict: CLEAN`、
コストは静的ページで変化なし、アニメーションするページで 2329ms → 2850ms）。

### 操作を、実際に起こす

`scan handlers --probe drag,dblclick,…` は探査（probe）を実行します。
現在の探査ファミリは 7 つ — `drag` / `wheel` / `hover` / `menu` / `touch` /
`input` / `dblclick`。どれも**ページ自身のハンドラを走らせて**、起きたことを
読みます。既定でオフなのは副作用があるからで、未知のファミリ名は黙って
何も測らずに通るのではなく `UsageError` になります。「測っていないのに緑」が
いちばん危険な失敗の形だからです。

`check interactions` は各コントロールにキーを送り、ARIA の状態遷移を
マップして、何にも繋がっていない disclosure を捕まえます。
`verify flow` はスクリプト化した動線を実行して、各ステップの結果をライブの
DOM 上で検証します。どれも「静止画を見る」の代わりではなく、
**時間と操作を測定に変換する**装置です。

## 3. だから二層で出す: 決定論的ルールセット + fuzzy なワークフロー

vlmkit が配っているものは 2 つあります。

### 下層: 決定論的ルールセット（0.11.1 時点で 27 ゲート / 171 ルール）

この数はテストがカナリアとして固定していて、増えても減りても落ちます
（意図した変更なら数字を更新する）。ここは「毎回同じ答え」が価値です。
設計の要点だけ:

- **kickback 形式**。失敗は「失敗」ではなく、欠陥・位置（CSS セレクタ）・
  測定値・多くの場合は修正の方向を出します。人間が読めて、エージェントの
  次のプロンプトにそのまま貼れる形です。
  ```
  x [page-overflow-x] @768: The page scrolls horizontally by 156px at 768px
    viewport width — sticking out: main > p:nth-of-type(1) (right edge 924px).
  ```
- **終了コードの契約が全ゲート共通**。suspect（欠陥レベル）はフラグ無しで
  非ゼロ終了、warn はどのフラグでも終了コードに影響せず、`--advisory` で
  print-and-succeed に戻せて、エラー（到達不能な URL、タイムアウト）は
  必ず失敗する。「欠陥を見つけたが exit 0」を既定にしないのは、
  無視する側に立証責任を置くためです。
- **ルール単位の抑制**。`vlmkit.gates.json` の suppression は理由が必須、
  owner と期限を持ち、期限切れは効かなくなり、`gates suppressions` で
  一覧できます。18 ルールのゲートを丸ごと切る、しかない状態を無くすため。
- **監査証跡**。すべてのゲート実行は `.vlmkit/run-ledger.jsonl` に 1 行 JSON で
  追記されます。エージェントが「検証しました」と言ったとき、ledger が空なら
  それ自体が finding です（実際に捕まえた記録があります）。
- **プラグイン構造**。ゲートは `defineGate` + 登録 1 行で、core はゲートを
  import しません。だから `@mizchi/vlmkit-core` は Playwright 無しで
  import できます（[`docs/design/gate-plugin-architecture.md`](../design/gate-plugin-architecture.md)）。

### 上層: fuzzy なワークフロースキル（1 エントリ + 11 ワークフロー）

一方で、**どのゲートをどの順で回し、どこで完了とするか**は決定論に書けません。
モックからの実装と、既存ページの回帰追跡と、フレームワーク移行の等価性検証は、
同じゲートの違う組み合わせです。ここは自然言語のワークフローにして
エージェントに読ませています。

インストールされる可視スキルは `vlmkit` 1 つだけで、11 の専門ワークフローは
その内部リソースです。ユーザーは「このモックを実装して、レスポンシブにして」
「このページのレイアウト・コピー・キーボード操作を見て」と言うだけで、
ルータが `mock-markup` + `dynamic-markup` や `markup-assist` を選びます
（[`.claude/skills/README.md`](../../.claude/skills/README.md)）。

**分担の理由は 1 行で書けます**。判定を fuzzy にすると再現せず、騙せる。
ルーティングを決定論にすると実際のタスクに当たらない。
エージェントは審判ではなく選手で、ゲートが審判、ledger が記録係です。

## 4. 実例: ソリティア

以上は設計の主張です。確かめるために、**ドラッグ&ドロップとアニメーションを
両方持つページ**を 1 本書きました。Windows の `sol.exe` を素の HTML/CSS/JS で
再実装した Klondike で、7 列のタブロー、4 つのファウンデーション、
ストックとウェイスト、HTML5 DnD、キーボード操作、勝利時のバウンド。

遊べます: <https://mizchi.github.io/vlmkit/solitaire/>
（ソースは [`examples/solitaire/`](../../examples/solitaire/)）

### なぜ Klondike なのか

- 52 個の要素が**毎手作り直される** — 現実の盤面と同じで、ハンドラは
  コンテナ 1 箇所に委譲するしかない
- ドロップの可否が CSS クラスではなく**ゲームルール**で決まる
- アニメーションが 4 種類（deal、めくり、ファウンデーション送り、勝利の
  カスケード）
- そして**正解の振る舞いが世界的に既知**。「Windows はどうだったか」で
  議論が終わる

ゲートのために URL パラメータを持たせています: `?seed=N`（配りを固定。
無いとスクリーンショットが毎回違い VRT baseline が無意味になる）、
`?draw=1|3`、`?animate=0`（deal は約 960ms かかるので、load 直後に撮る
ゲートは空中のテーブルを掴む）。依存なし・ビルドなしで `file://` から動き、
カードは画像ではなく描画された**本物のテキスト**です（`check copy` と
スクリーンリーダーが読めるように）。

### ゲートを向けた結果

| ゲート | 結果 |
|---|---|
| `check animation` | **良好**。8 つの deal アニメーションを検出、`settle: 962ms`、`reduced-motion: honored`、issue なし |
| `check interactions` | **良好**。13 コントロールを探査し、真陽性 1 件 |
| `check a11y focus` / `check a11y touch` | 正しく 0 件 |
| `scan handlers --probe-drag` | 4 件のうち **3 件が偽陽性**（イベント委譲） |
| `check a11y contrast` | **9 件の偽陽性**（グラデーションの背後を白と仮定） |
| `check integrity` | **1 件の偽陽性**（アニメーション途中のフレームを測定） |

真陽性はこれ:

```
warn [inert-control] button "Restart this deal" shows no observable response to Enter
```

正しい指摘でした。同じ配りの初期局面を再描画すると**ピクセルは完全に同一**で、
アナウンスもライブリージョンに既にあった文と一語一句同じ。つまりボタンには
本当に観測可能な効果が無かった。今はどの配りを再開したか言います。

偽陽性 3 件は、**すべてツール側の修正**になりました。

1. **drag ルール 3 つがイベント委譲を知らなかった**。コンテナは draggable では
   なく、その子カードが draggable。`dragover` は**ルールが受理する手のときだけ**
   `preventDefault` する — それが機構そのものです。探査は 1 組しか試して
   いなかったので、「一度も cancel しない」と「この対象を正しく拒否した」を
   区別できなかった。今は source×target を探索し（上限 96）、どの組も
   cancel しなかったときだけ報告します。途中のバージョンは**バグより悪く**、
   兄弟要素の `preventDefault` を当該要素のものとして報告していました
   （`dragover` はバブルするので、対象は自身の部分木に限定されます）。
2. **`check a11y contrast` がグラデーションの背後を白と仮定していた**。
   ツールバーは緑のグラデーション上の `rgba(0,0,0,0.28)`、文字はほぼ白。
   つまりページの中でいちばんコントラストが高い箇所で、ゲートは 1.08:1 と
   **逆**を報告しました。同じページで `check integrity` は正しく
   「合成背景は決定論的に測れないのでスキップした」と言っていた —
   免除はツールキットに存在していて、コントラスト専門のゲートだけが
   持っていなかった。今は背景解決が 1 つの共有定義で、
   `background-image` があれば**推測せず拒否**します。
3. **`check integrity` が捕まえたフレームを測っていた** → 前述の `settlePage`。

### 逆に、ゲートしか見つけられなかったもの

| 見つけたもの | 欠陥 |
|---|---|
| `check integrity @375` | **スマホ幅で 14px の横スクロール**。狭幅のカード幅が手打ちの `3.3rem` で、その上のコメントは「オーバーフローしない」と主張していた。今は制約（7 列 + 6 ギャップ + パディングが収まる）から導出され、320px〜1280px で 0px |
| `check integrity @375` | 縮むカードの上で中央のピップが固定 `1.5rem` のままで、375px で角のインデックスと衝突（`text-collision` 10 組） |
| `game.test.mjs` | **山（pile）に `tabindex` が無く、フォーカスが当たらなかった**。ヒントは「Tab で山へ」と書いてあり、文書化されたキーボード導線が到達不能だった。`check a11y focus` は 0 件 —**カードは**到達可能だったので。見つけた tab 順は検査できても、ページが主張する tab 順は検査できない |
| `rules.test.mjs` | `availableFoundationMoves` が 3 枚のエースすべてにファウンデーション 0 を返し、auto-finish が 3 手のうち 2 手を黙って捨てていた |

### 「勝てること」を証明する

ユニットテストの勝利ケースは自分で *"Rigged rather than played"* と書いています
（完成状態を代入して Auto-finish を押す。実際の勝利は約 150 手）。つまり
**勝てないソリティアがテストを全部通る**状態が一時期ありました。

閉じ方が 2 ファイルの分担です。`solve.mjs` が「この配りはそもそも勝てるか」
（DFS + 局面シグネチャのメモ、ブラウザなし、seed 1-6 は 145〜24k ノードで
300ms 未満）、`playthrough.mjs` が「ページはそれを正しく指せるか」
（その手順を実 UI で再生し、**毎手 DOM を state と突き合わせて監査**）。
2 つが食い違ったら、それ自体が finding です。

監査は毎手こう見ます: 52 枚がストック/ウェイスト/タブロー/ファウンデーションに
ちょうど 1 回ずつ、各ファウンデーションは同一スートでエースから昇順、
表向きの隣接ペアは降順かつ色違い、表向きの上に裏向きが無い、
各山でカード 1 枚につき DOM ノード 1 つ、両カウンタが state と一致。
バグを 4 種類注入して、報告に名前が出ることを確認しています:

| 注入 | 報告 |
|---|---|
| 7 手ごとに `render()` を飛ばす | `ply 14 — tableau 4 holds 9 cards and renders 8` |
| `applyMove` 1 回でカードを落とす | `move 13 — the table holds 51 distinct cards, not 52` |
| `canStackOnTableau` が色を無視 | `move 1 — tableau 0 stacks hearts-11 on hearts-12, which is not a descending alternating run` |
| `celebrate()` を呼ばない | `the game is won and the win banner is still hidden` |

seed 1 は 144 手で 52/52。`commit` 経由で 8 秒、実ドラッグ経由で 14 秒。

### 人が遊んで見つけた 3 件が、ルールになった

いちばん面白かったのはここです。人間が手で遊んで報告した 3 件について、
**なぜどのゲートも何も言わなかったのか**を調べたら、2 件がルールになりました。

- 「ある操作列で範囲選択になって、その後カードを何枚か掴んでも何も起きず、
  戻る方法が無かった」 → **探査が、報告すべき欠陥を自分で消していた**。
  どの探査もジェスチャの前にテキスト選択をクリアします（選択されたテキスト自体が
  draggable で、残った range が次の測定を変えるので必要な処理です）。
  そしてクリアするだけでした。今は**クリアする前に読みます**。
  ルール 2 つ: `drag-selects-text`（range が**アンカーした要素**に名前を付ける —
  `user-select: none` が必要なのはそこで、多くの場合ヒント行やステータス表示で
  あって操作面ではない）と `dblclick-selects-text`（ハンドラが適用されない点を
  わざと double-click する）。手で 4 通り再現しましたが、**どれもカードの上から
  始まっていません**。だから `.card { user-select: none }` は一度も効かなかった。
  シェル側に `user-select: none` を置いて、ルールは修正前に鳴り、修正後に黙り、
  5 つのジェスチャすべてが 0 文字を選択します。
  なお「戻れない状態」は**再現しませんでした**。仮定せずに未再現として記録。
- 「ドラッグ中、掴んだカードが半透明になって背後と混ざり、どのカードか
  分からない」 → `drag-ghost-illegible`。要素を静止時と飛行中に撮り、
  暗い側 2% と明るい側 10% の WCAG 比を両方報告します（ink 分位が 2% なのは
  実測から: カード面は 90% 以上が紙で、最も暗い**十分位**はほぼアンチエイリアス
  になり、同じカードで 4.06:1 と 6.17:1 に分かれた）。
  評価は**低下率と床の両方**で、片方だけでは決めません。15:1 が 9:1 に落ちる
  ページは同じ割合を失っても読めますし、静止時に低コントラストなら
  それは `check a11y contrast` の仕事です。
  結果、ソリティア自身のケース（`opacity: 0.55` で 7.59:1 → 5.01:1、34% の低下で
  4.5:1 の上に着地）は**出力されるが判定されません**。人が見て欠陥と呼んだことを、
  ルールが証明したと主張してはいけない。直し方はカードを暗くするのではなく
  **置き場所を示す**方向に変えて（0.92 のまま破線アウトライン）、
  7.59:1 → 7.54:1 になりました。
- 「空になったストックが、めくり直せることをスクリーンリーダーにだけ伝えて
  いた」 → `aria-label` は "Stock empty — turn the waste over" で正しく、
  ピクセルは何も残っていない山と同じアウトラインでした。
  **どのゲートも捕まえられません**。アクセシブル名は正しいのだから。
  `render()` が 1 つの `stockState` から label と `[data-state]` の両方を書くように
  して、二度と乖離しないようにしました。一般形は「操作できるのに何も見せない」で、
  静的ゲートに見えないのはストックが**クリック 20 回以上の後にしか空にならない**
  から。そこへ到達するのは `verify flow` の仕事です。記録して、解決していません。

このループの形が結論です。**fuzzy な側（目、手、実際に遊ぶこと）が見つけ、
決定論の側が固定する。** そして固定した後は、ソリティアのページ自身が
再現ケースになります — 修正が回帰すれば、また鳴る。

## 6. 境界

信頼は明示された境界に宿るので、重要なものを 2 つ。

**緑のゲート集合は正しさの証明ではありません。** ゲートは符号化した欠陥クラスを
捕まえます。だからこのプロジェクトは偽陰性を面倒な方法で追っています —
評価実行ごとに、全ゲートが見逃した欠陥を独立に監査して記録する。
この記事の 1 節目の表がまさにその記録です。

**目は今も必要です。** ソリティアで最後まで残った 4 件は、すべて
「マークアップは妥当・ラベルあり・到達可能・コントラスト十分で、**意味**だけが
間違っている」形でした。スートを守らないスートのヒント、変な場所に折り返した
リンク、コントロールから切り離されたラベル、別のものとして読める数字。
決定論的ゲートの境界はここで、知っておく価値があります。

エージェントの目とルールセットは競合しません。役割が違う。
**見つけるのは目、決めるのはルール、記録するのは ledger。**
