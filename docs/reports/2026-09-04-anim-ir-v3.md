# anim-ir v3: do `after` and `goto` close the v2 failures? (2026-09-04)

## Question

v2 found two IR flaws from the re-edit axis: absolute event times drifted
when a message latency changed (agents g, h), and a warning's hint named a
remedy the state-machine kind lacked, so an agent deleted the path the brief
required (j). Both were fixed — `after` anchors on distributed events and
messages; `{"goto"}` / `{"note"}` / `{"on", "caption"}` trace items — and this
run re-issues the same tasks against the fixed tool:

| agent | model | task | what it re-tests |
|---|---|---|---|
| k | sonnet | re-edit: same change request as v2, on the same story rewritten with `after` anchors (`re-edit/README-v3.md`) | does the crash / promotion survive a latency change without hand re-timing? |
| l | haiku | same | same, on the smaller model |
| m | haiku | TCP teardown brief with the alternative path, **zero warnings required, path must stay** | is the untaken-path hint now followable? |
| n | haiku | Raft election brief (fresh author), then a forced latency change as an experiment | does a new author reach for `after` unprompted, and does their story survive? |

## The agents' words

### Closed — drift on re-edit (k, l, n)

> Timing survived without manual re-timing — `explain` confirms crash still sits exactly 2 steps after "ok", promotion still combines with "client retries…" at the same step; only absolute ms shifted (3780ms → 5580ms). (k)

> No manual re-timing needed. … The `"after"` anchor mechanism kept events moving with their referenced messages. (l)

> Why this choice (from guide): "Prefer `after`: an absolute `at` stays put when you lengthen a latency upstream." (n)

The construct is used correctly by a fresh author who has only read the
guide, and it does what the re-edit needed. g's v2 complaint — that the
events' timing intent was not readable from the file — is answered by the
file itself now: `{"after": "ok", "delay": 100, …, "caption": "primary crashes"}`.

### Closed — the untaken-path hint (m)

> This passage mapped directly: "trace... `{goto: state, caption: …}` to jump the token without a transition — how you show a second path after the first has ended." This is exactly how I showed both the normal path … and then the simultaneous-close alternative. (m)

Same model, same brief, same zero-warning rule as j in v2: clean on the first
attempt with the alternative path kept and narrated.

### G9 — `delay` without `after` was a silent no-op (k)

> `"delay": 1200` alone (no `after`) silently produced zero timing change and no warning — nothing in the field signals it's a no-op without a paired anchor. (k)

k's round 1 passed `check` clean and changed nothing. **Fixed in this
commit:** `delay` without `after` is a validation error on messages and
events, with the hint naming both fixes (`after` for a gap before sending,
`latency` for a slower message). k's round-1 file now fails with exactly that.

### G10 — inserting a message pushed the main line (k, l)

Both agents added the `replica → backup` copy in list order right after the
ack, which is what the task said. With list-order timing, the primary's `ok`
then waited for the copy to land: `ok` moved from 2400ms to 3000ms (l) and
3600ms (k). Neither agent noticed — `check` is clean, the anchored events
followed `ok` correctly, and `explain` shows the shift only as a number.
Nobody said the story was broken, and arguably it is not; but "nothing else
changes" was the brief, and the main reply got slower because a side branch
was inserted before it.

**Partly fixed in this commit.** The guide now states the rule — inserting a
message delays everything after it; anchor a side branch with `after` (and
the message it would push) — and, from n's separate ask below, `"at": "<"`
lets a message leave together with the previous one. Not fixed: the tool
cannot tell an intended reordering from an accidental one, so there is no
check. If a fourth run shows the same slip, the default itself
(list order = strict sequence) is the thing to revisit.

### Also — no way to write a broadcast (n)

> The guide shows sequential message examples but doesn't explain how to send two messages in parallel … The vector kind's `"at": "<"` syntax ("together with previous") would be helpful here (n)

**Fixed in this commit:** `"at": "<"` on a distributed message starts it with
the previous one, as in `vector`.

### Readability notes carried forward (k, l)

> Unsure of: what `events[].after` anchors to (send vs. arrival) … why promotion anchors to the *lost* `write x=2` rather than `retry x=2` (k)

> The semantic difference between `latency` (message transmission time) and `delay` (event pause after anchor) … Someone editing without the guide might assume … slow-disk latency should use `delay` instead of `latency`. (l)

Both resolved from the schema sheet in one look, and k and l modelled the
same "slow ack" differently (l: `latency: 1200`; k: `after: "replicate x=1"` +
`delay: 1200`) — both legitimate readings of "acknowledges after a 1200ms
delay", so the IR is expressing a real ambiguity in the brief rather than
adding one. Left as is.
