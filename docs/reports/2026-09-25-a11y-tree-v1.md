# Accessibility from a platform tree, v1: ofc-app as the measuring stick

**Question.** A Flutter web project ([whywaita/ofc-app#36](https://github.com/whywaita/ofc-app/pull/36))
adopted vlmkit and had to work around it three times:

- A static server that injects a click on `flt-semantics-placeholder`.
- Three `check integrity` rules turned off, because Flutter's accessibility DOM paints nothing.
- A hand-written, 200-line pixel contrast audit.

Can those workarounds become a contract that also serves Android, iOS, macOS and Windows,
where there is no DOM at all?

**Answer.** Yes. The contract is `vlmkit-a11y/1`: role, name, rect, states and actions, plus
the frame. Two gates use it:

- `scan a11y` (Flutter web and Android `uiautomator dump` today).
- `check a11y tree` (four rules; no browser).

On ofc-app's pre-fix build, `check a11y tree` reproduced the project's two contrast and naming
findings, and found one defect that the project's own audit could not see.

## Setup

- **Pre-fix:** ofc-app `6aaf448`, the last commit before #36's fixes, built with Flutter
  3.47.5 (`flutter build web --release`).
- **Post-fix:** the deployed build (`main`, the same engine `af7e796e`).
- **Serving:** CanvasKit and Roboto came from `gstatic.com`, which this sandbox's Chromium
  cannot verify through the egress proxy. So both builds were replayed from a HAR:
  - the local build's files;
  - the CanvasKit and font responses, fetched through Node, which trusts the proxy CA.

  TLS verification stayed on throughout. The app itself was not modified.
- **Screens:** home at 375x812, and `--click Practice --click Start` at 375x812 and at 375x568.

## Results

| screen | pre-fix | deployed fix |
|---|---|---|
| home | `contrast-below-aa` "Game Mode" **4.38:1** (#757575 on #F4FBF8) | clean: "Game Mode" 5.89:1 |
| game | `unlabelled-control` the seed line's `<textarea>` (130x26, disabled, no name) | the seed line is plain text; no textarea |
| game | `contrast-below-aa` every red card, **3.68:1**, 14px | same: still 3.68:1 |
| game | — | the 17px "Place in Top/Middle/Bottom" buttons are `enclosed` by their 35px tappable rows, not failures |

Against #36's seven defects:

- **Found (2):** the `Game Mode` contrast and the unlabelled seed field.
- **Not reached (1):** the unreachable Action Log is on the result screen. The pre-fix build
  reaches that screen only by dragging cards, and `--click` cannot drag. The fixed build adds a
  tap path but also fixes the scroll, so no single commit has both. The rule is covered by the
  fixture and the Android test.
- **Not decidable from the tree (3):** "no hint how to drag", "a refused drop says nothing" and
  "missing `cupertino_icons`" (which is a build warning, not an a11y finding).
- **Found late (1):** the seed line's own contrast (2.55:1). The pre-fix tree gives that text no
  name, so it has no node to measure. It becomes measurable once the unlabelled finding is fixed
  and the text gets a node. The findings arrive in the order a repair would take them.

The red cards are the round's new finding. Material red 500 on white is 3.68:1, and the card
labels are about 14px. ofc-app's `contrast-audit.mjs` chose the floor from the rect's height
(24 and up counts as large text), so a 40x30 card was held to 3:1 and passed. `check a11y tree`
measures the inked text height instead (13 rows / 0.9 = 14.4) and holds it to 4.5:1.

## What the round changed in the code before it was right

Three defects came from the real app. None of them came from the fixture I wrote first:

1. **Outlines counted as text.** Every mode chip measured as 35.6-unit text, because its
   outline's rows counted as ink. That gave the chips the lenient 3:1 floor, and it could let
   the outline's colour stand for the label's. Fix: split the ink into connected components and
   drop the ones that span the rect as a rule or an outline.
2. **The first fix over-corrected.** Dropping every width-spanning component made the pre-fix
   build's tight `"7♥"` card rects read as blank ink. Fix: drop a component only when it spans
   the width *and* is thin or spans the height too. Mutation-checked in both directions.
3. **A Flutter build crashed without a locale.** `new Intl.Locale(...)` threw at startup in a
   container with no `LANG`, so the app never booted, and the page read as "not Flutter".
   `scan a11y` now pins `en-US` (`--locale` overrides it), so the capture does not depend on the
   host.

Two policy calls were made on the same data:

- **`unlabelled-control` judges disabled controls.** Flutter renders `SelectableText` as an
  empty, disabled `<textarea>`, and WCAG 4.1.2 has no inactive exemption. Only 1.4.3 does, and
  the contrast rule still honours it.
- **Nested targets are judged by their enclosing target.** The row takes the same tap as the
  17px button inside it, so the button is listed as `enclosed` rather than failed.

## Next

- `scan a11y --flow flow.json`: run a `verify flow` file (click, fill, wait) before collecting,
  so a screen that needs a typed seed (ofc-app's `play-hand.flow.json`) can be reached. `--click`
  covers taps only.
- Collectors for the other platforms, as scripts writing the same JSON: macOS AX, Windows UIA,
  iOS XCUITest, and a Flutter `SemanticsNode` dump for desktop and mobile.
- Focus order from the tree's order, without pressing Tab. `check a11y focus` raced Flutter's
  asynchronous semantics on ofc-app (3 failures in 10 runs).
