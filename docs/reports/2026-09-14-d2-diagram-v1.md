# d2-diagram v1: can an agent draw a *correct* D2 diagram from the skill alone? (2026-09-14)

## Question

The `d2-diagram` skill shipped in [#148](https://github.com/mizchi/vlmkit/pull/148)
claims that the TALA terminal render is how a writer checks its own picture, and
says outright that "a D2 diagram is a drawing, and nothing in D2 tells you it is
wrong". This round tests both halves: can four fresh writers, given one brief and
the skill, produce a diagram that is **factually** right, and does the loop as
written tell them when it is not?

Procedure: `.claude/skills/agent-validation-loop`. Each writer got one brief from
`fixtures/d2-scenario/briefs/`, the skill and its assets, a 5-round budget, and
`d2` v0.8.1-HEAD. Forbidden: the other briefs, each other's attempts, and
`briefs/facts/` — the fact sheets exist only for scoring, because in v1 the
writers are supposed to check their own work the way the skill says to.

| writer | model | brief | what it draws |
|---|---|---|---|
| a | default | `order-events` | 11 boxes, 3 regions, a broker fan-out, ≤ 100 columns |
| b | default | `shop-schema` | 5 `sql_table`s, 4 column-level foreign keys, ≤ 100 columns |
| c | default | `checkout-calls` | `sequence_diagram`, 7 messages with returns and one async, ≤ 80 columns |
| d | haiku | `order-events` | the same brief as a, second model size |

## Result

Scored after the fact with the sheet the writers never saw
(`assets/d2-facts.mjs --expect`, written during this round — see below).

| writer | own done condition | fact errors | columns | rounds |
|---|---|---|---|---|
| a | met | **0** | 75 | 4 |
| b | met | **0** | 76 | 5 |
| c | met | **0** | 75 | 4 |
| d | met | **9** | 94 | 5 |

Three of four diagrams are correct. The fourth is the round's finding: it met
every check the skill names, and its picture is wrong in a way its writer could
not see.

### Writer d: four phantom boxes, and a log that says the opposite

`d2 validate` 0, `d2 fmt` clean, 94 columns, and the log's last line reads "can
trace all connections". What the render actually contains:

```
┌──────────┐          ┌───────┐
│ gateway  │─────────▶│orders │      ← a floating pair outside every region:
│          │          │       │        the system's entry call
└──────────┘          └───────┘
```

plus `browser` inside **Edge** and `Browser` inside **Outside**, `stripe` floating
and `Stripe` inside Outside — four duplicated names, two orphans, and the
`gateway -> orders` call disconnected from both real services.

The cause is one D2 rule the skill did not mention: **a reference to an id that is
not in scope creates a new shape.** Line 53 of the attempt is `gateway -> orders`
at the root, where the real shapes are `edge.gateway` and `cluster.orders`, so D2
silently added two more boxes and drew the arrow between *those*. Inside the
`edge` container, `browser -> cdn` did the same for `browser`. Round 5's own
"fix", `billing -> _.stripe`, created the fourth: from inside `cluster`, `_` is
the root, and `stripe` lives in `outside`, so the correct reference is
`_.outside.stripe`. The log for that round says "stripe duplication resolved"
while the render duplicates stripe.

Nothing in `validate`, the renderers, or the terminal render flagged any of it.

## What was fixed in this commit

### 1. `assets/d2-facts.mjs` — the check D2 does not have

D2 has no `--expect` and no layout report. It does, however, write **every
shape's and every connection's fully-qualified id into the SVG** (base64 in a
`class` attribute), with per-shape geometry and labels. So the drawn picture can
be read back:

```
$ node d2-facts.mjs order-events.d2 --expect order-events.expect.json
  ✗ "gateway" is drawn 2 times (gateway, edge.gateway) — a reference to an id that is
    not in scope creates a new shape; use a full path or `_.` to reach out of a container
  ✗ edge reversed: the sheet says broker->billing, the picture draws billing->broker
  ✗ edge not drawn: billing->stripe (looked for cluster.billing->outside.stripe)
✗ order-events.d2: 18 ok, 7 warning(s), 9 error(s) · 94 columns · 11 edges drawn
```

It reports, with a sheet: every listed box drawn, every listed edge drawn **with
its direction**, forbidden edges absent, container membership, a sequence
diagram's message order (read back from the connections' y positions — the one
place D2 makes order visible), and the width. Without a sheet it still fails on
the two defects that are always defects — a name drawn twice, a box overlapping a
sibling or escaping its container — and warns about a box nothing connects to.

Names match an id's last segment **or its label**, which is not cosmetic: writer a
abbreviated its ids to `gw` and `pg` in round 3, and an id-only matcher scored its
correct diagram as four missing edges. The first version of this scorer did
exactly that, and the fix is in the shipped asset.

It cannot see inside a `sql_table`: `orders.customer_id -> customers.id` is
reported as `orders->customers`, and constraint badges are not checked. That is
written down in the skill rather than papered over — writer b had to
`grep -c '>FK</text>'` its own SVG for the same reason.

`assets/vlmkit-workspace.facts.json` is the example's own sheet, so the skill
ships a worked pair.

### 2. Six corrections the writers proved, in their words

- **"`foreign_key` is nowhere in the skill.** The route row gives `primary_key`
  only, and a data-model brief is *about* foreign keys. I guessed
  `{constraint: foreign_key}` from prior D2 knowledge" (b). Now in the row.
- **"Both documented width levers made this file wider."** `direction: down` gave
  145 vs 144 and shorter labels 146 (a); on b's schema the same `direction`
  change was the 148 → 109 win. The lever that worked for a — per-container
  `direction` on the container holding the most boxes, 146 → 113 — "is mentioned
  only as a modelling nicety, never as the width lever". The skill now carries the
  measured two-diagram table, says the levers are non-monotone, and puts the
  fullest container's own `direction` first.
- **"`--tala-seeds 4,5,6` *gives you a different layout*"** — misleading as
  stated: b swept twelve seed sets over one schema and got the identical
  109-column layout every time, while a moved 113 → 100 with one. And **seeds
  cannot live in the file**: `d2 layout tala` advertises "diagram data under
  tala-seeds takes precedence", but `vars.d2-config.tala-seeds` is rejected at
  compile time, so a committed diagram cannot carry its own seed (a).
- **"The skill never says styles are dropped in `.txt`."** c diffed its styled
  render against a style-free copy: **identical**. `stroke-dash` for a return or
  an async event is invisible in exactly the deliverable its brief graded, and c
  had trusted round 1's returns. Also unmentioned: `<<` in a label is eaten, and a
  long label can leave its arrow with no head. All three are on the dropped list
  now, with "say it in the label" in the sequence-diagram row.
- **`wc -L` undercounts.** "It reports 70 vs 75 for the *same* layout — by display
  columns both are 75" (c). Measured: on the example figure `wc -L` says 120 in
  the C locale and 122 in `C.UTF-8`; on a Japanese figure, 87 against a true 111;
  and `awk '{print length($0)}'` reports **338 bytes** for a 122-column render.
  The skill now names `LC_ALL=C.UTF-8 wc -L`, and `d2-facts` prints the same
  number as `columns`.
- **The version claim was wrong** — all three of a, b and c flagged it. "`d2
  --version # v0.9.0 or newer bundles TALA` … the installed v0.8.1-HEAD lists
  `tala (bundled)`. Following the skill I would have tried to upgrade first" (a).
  The gate is now `d2 layout` listing `tala (bundled)`, not a version string.

### 3. Two loop steps that were there but unusable

- **`_` and cross-container references** were one parenthetical inside a rules
  bullet. Writer d, the one that shipped phantoms, "discovered underscore escaping
  by trying it" and still got the depth wrong. It is now in the architecture route
  row, in the rules with the `_.outside.stripe` depth spelled out, and in a
  dedicated section with d's render as the worked example.
- **"look at it once with your own vision"** worked for c ("Step 4's PNG read
  caught round 4" — a dashed event that looked like a return) and did not for d,
  which wrote "the SVG would confirm this but isn't readable in a terminal". The
  loop now says to render the `.png` and **read the file**, because an agent can
  look at an image.

## What is deferred

- **Column-level edges and PK/FK badges** are invisible to `d2-facts` (the SVG
  carries no per-row ids) and to the terminal render. Both are in the skill's
  limits list. A sheet that wants them needs the SVG text grep, which is too
  fragile to ship as a check.
- **Box-collision reporting** exists for siblings only. Writer a could not tell
  whether `shipping` and `redis` "overlap or merely touch" across containers; the
  sibling check would not have answered it either.
- **"Whether the layout is *good*, only that it is narrow and correct"** (a). The
  100-column budget left an almost-empty region box and a container label
  overflowing. `vlmkit-anim`'s answer to this is `review --still` with a vision
  reader; D2 has no equivalent and this round did not build one.
- **A v2 round** with the fact sheet in the writers' hands, which is the
  comparison v14 made for `anim-ir`: does a writer with a sheet get it right
  first time? d's nine errors are the number to beat.

## Honest read

The skill's route table and shape vocabulary worked: all four writers produced a
valid, well-shaped diagram on the first write, and three were factually correct
with no help beyond the prose. Everything that went wrong went wrong in the
*checking* half, exactly where the skill admitted it had nothing — and the smaller
model is where that cost a correct picture. The round's output is therefore one
asset and a page of measured corrections, not a rewrite: `d2-facts.mjs` turns
"nothing tells you it is wrong" into nine lines that do.
