# anim-ir v4: should the distributed timing default change? (2026-09-04)

## Question

v3 left one open item, G10: with list-order timing ("a message starts when the
previous one in the list lands"), both re-edit agents inserted a side branch
after the ack and the primary's reply silently waited for it. Two candidate
answers: keep the default and teach the insertion rule (done in v3's guide), or
change the default to a **causal** model — a message starts when its *sender
is free*: after the last message the sender received has landed and its own
previous message has landed. v4 ran both on the same edit, plus a fresh
author under causal to see whether the model surprises someone writing from
scratch. The README for both arms gained the explicit criterion "the primary
must still confirm to the client as soon as the ack reaches it".

| agent | model | arm | context |
|---|---|---|---|
| o | sonnet | A: sequential default + guide rule | re-edit `replication-after.scene.json` |
| p | haiku | A | same |
| q | sonnet | B: `"timing": "causal"` | re-edit `replication-causal.scene.json` (same story) |
| r | haiku | B | same |
| s | haiku | B, fresh author | Raft brief with `timing: causal` required; asked to predict every start time before the first `check` |

## Result

| agent | first `check` | rounds | `ok` still sent when the ack lands? | anchors the agent had to add for that |
|---|---|---|---|---|
| o | clean | 1 | yes | `after: "ack"` on `ok` and on `copy` — "the guide's own example is literally this task" |
| p | clean | 1 | yes | `after: "ack"` on `ok`, `"at": "<"` on `copy` |
| q | clean | 1 | yes | none needed ("causal scheduling isolated the new backup branch automatically"); added one `after` anyway |
| r | clean | 1 | yes | one `after` on `copy`, not needed |
| s | clean | 1 | — | fresh scene: **0 surprises** between predicted and actual start times for every message |

Both arms reach the right timing. The difference is in what got them there:
arm A needed the writer to notice the hazard and add two anchors, and knew to
because the guide names this exact task; arm B needed nothing. In v3, with
no guide rule, arm A's condition scored 0/2.

### Decision: `causal` is the default

Evidence, in order of weight:

1. **Re-edit under causal was correct without effort** (q, r), and under
   sequential it was correct only with effort that a v3 agent did not make
   (k, l) and a v4 agent made because the guide happened to describe the
   task (o: "the guide's own example is literally this task"). A default
   that needs the doc to name your exact situation is the wrong default.
2. **Fresh authors are not surprised by it.** s predicted every start time
   under causal and got all of them right on the first attempt, including
   the broadcast (`"at": "<"`) and the lost request.
3. **Every agent who used it wants it.** r: "Causal is easier and should be the
   default." q: "I'd default to `causal` for anything with branches/replicas;
   `sequential` still reads more plainly for a single linear chain." s:
   "HARDER to learn but EASIER to use once learned … The model self-corrects
   insertion."
4. **Blast radius is small and points the right way.** Recompiling every
   distributed scene in the repo under causal: fixtures and every scene
   without an inserted branch are identical; the six that change (g, h, k, l
   and the two causal-arm files) change exactly into the "ok not pushed"
   timing the task wanted. One v1 scene (c) shifts its vote requests earlier
   because it relied on list order for an unstated timeout — the case causal
   asks a writer to make explicit with `{"after": …, "delay": …}`.

`"timing": "sequential"` stays as an opt-in, for q's linear-chain case.

## The agents' words

> Every beat that moved shifted by exactly the one +1200ms delay I introduced; every relative gap stayed identical. Nothing moved that shouldn't have, and `copy` never delayed `ok`. No extra anchoring was needed to prevent drift — causal scheduling isolated the new backup branch automatically. (q)

> With sequential timing, inserting it would delay ok; I'd need to anchor both with `"after": "ack"` and adjust delays. With causal, one `"after"` on backup, and ok naturally starts when the primary is free — no synchronization needed. (r)

> Surprises: 0. Every single timing matched my expectation exactly. (s, fresh author)

> `ok` got `"after":"ack"` added explicitly (required because the new backup message now sits between `ack` and `ok`, and unanchored messages default to firing after their array-predecessor). (o, arm A — the work causal removes)

## Friction fixed in this commit (s)

> The guide … does NOT warn that using the same label for multiple messages breaks `after` anchoring. (the validator caught it; the guide now says labels used as anchors must be unique, and that a broadcast needs one label per destination)

> Causal … is accurate but hard to parse on first read. A worked example would help (the guide's causal paragraph now carries a four-message worked example with the reason for each start time)

> `delay` … listed without explanation (now: "milliseconds after its `after` anchor lands")

The package fixture `distributed-replication.json` also moves its events to
`after` anchors; it was the last scene in the repo still carrying an absolute
event time mid-flight.

## Carried forward, not fixed

- o: "`\"lost\": true` gives no explicit 'would-be arrival' — the promotion
  event depends on an implicit virtual-landing computation." True: a lost
  message still "lands" for anchoring purposes at send + latency. The guide
  states `after` anchors to a landing; adding "a lost message's landing is
  when it would have arrived" is a one-line doc fix left for the next pass.
- p: `"at": "<"` "is cryptic. First re-editor might not know it means
  'broadcast' without the guide." It is borrowed from `vector` and the
  framer-style timelines it imitates; a spelled-out alias (`"with-previous"`)
  would cost nothing and is worth doing if a third agent says so.

## Stopping

Four runs, nineteen agents. The last two runs' fixes were a default and doc
sentences; the last new construct forced by a failure was v2's. Remaining
items are one-line doc notes. Per the loop's own criteria this is the point
to stop: release-prep (CHANGELOG at release time, since `version.test.ts`
pins the top heading to the shipped version) and merge.
