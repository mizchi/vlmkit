# Demo sites, and how each one was judged

Six static sites, each built by a fresh agent from a one-page brief using vlmkit's gates and its own
eyes, each published next to the log of how it was judged:
<https://mizchi.github.io/vlmkit/sites/>.

| Site | Pattern | Brief |
|---|---|---|
| [`docs/`](docs/) | documentation site (three pages, drawer, scroll-spy, themes) | [`briefs/docs.md`](briefs/docs.md) |
| [`shop/`](shop/) | e-commerce product page, Japanese (swatches, cart drawer, reviews) | [`briefs/shop.md`](briefs/shop.md) |
| [`dashboard/`](dashboard/) | analytics app shell (charts, sortable table, dark by default) | [`briefs/dashboard.md`](briefs/dashboard.md) |
| [`magazine/`](magazine/) | long-form article, Japanese (footnotes, reading progress) | [`briefs/magazine.md`](briefs/magazine.md) |
| [`checkout/`](checkout/) | multi-step checkout (validation, promo code, sticky summary) | [`briefs/checkout.md`](briefs/checkout.md) |
| [`kanban/`](kanban/) | task board (drag and drop with a keyboard alternative, dialog) | [`briefs/kanban.md`](briefs/kanban.md) |

The landing page (`../vlmkit-intro-page/`) has a log of the same kind: a visual review, from
[`briefs/landing-review.md`](briefs/landing-review.md), which is the first time anyone kept a record
of looking at it, and a fourth round judging the links to this gallery. The gallery itself
([`index.html`](index.html), generated by [`gallery.mjs`](gallery.mjs)) was judged the same way and
has its own log, [`JUDGMENT.md`](JUDGMENT.md). Across the eight logs, 135 of 179 defects were found by
looking and 44 by a gate: [`docs/reports/2026-09-23-demo-sites-v1.md`](../../docs/reports/2026-09-23-demo-sites-v1.md).

## Why the logs exist

A gate's output is easy to keep and easy to trust. What the builder *saw* is neither: the landing
page's earlier visual findings survive only as sentences in commit messages, with no picture of what
was looked at, so nobody can tell a judgment made by eye from a guess — or check that it still holds.
Solitaire's README shows how much that half is worth: every defect in its "found by screenshot" rows
was markup that was valid, labelled, reachable and contrast-clean while meaning the wrong thing.

So each site keeps both halves in one file, `judgment.sqlite`, written by [`judge.mjs`](judge.mjs)
while the work happened, under one [protocol](PROTOCOL.md):

- **every gate run**, with its exit code and its whole output;
- **every screenshot**, one screen per image at native resolution, and a **look** — what was seen in
  it — recorded against the image it describes. Once a round is done, the log keeps the pictures of
  one full-page walk per width (desktop, tablet, phone) and lets the builder's working views go;
  what was seen in them stays;
- **every defect**, with the look or gate run that found it, the fix, and the later look or run that
  checked the fix.

The published page is rendered from it (the Pages build reads the page and its screens out of the
database); `JUDGMENT.md` is the same log as text, for reading on GitHub, each shot and gate run linked
to that page. `judgment/` next to the database is a local export — what `shot` writes for the builder
to Read and what `render` writes — and is never committed. The database opens in any SQLite reader:

```sh
sqlite3 examples/sites/docs/judgment.sqlite "select id, json_extract(json, '$.cmd') from events where kind = 'gate'"
sqlite3 examples/sites/docs/judgment.sqlite "select text from outputs where path = 'gates/G12.txt'"
```

## Running the tool

```sh
J="node examples/sites/judge.mjs examples/sites/<name>"
$J init --title "…" --pattern "…" --brief examples/sites/briefs/<name>.md
$J round "first draft"
$J gate check integrity index.html                 # any vlmkit command, run in the site directory
$J shot index.html --full --viewport desktop,mobile # prints one file per screen — Read them
$J look S1 - <<'EOF'
…what is in the picture…
EOF
$J defect --from L1 "…"      # or --from G3
$J fix D1 "…" && $J verify D1 --by L5
$J check && $J done "…"      # done refuses until check passes, then renders
$J render                    # JUDGMENT.md, and judgment/ — the page with its screens — to open locally
```

`--help` lists the rest. `check` is the log's own done condition: every screen looked at, every
defect fixed and verified or closed with a reason, the last round with a gate run and full-page shots
at desktop and phone width, and the last run of every gate command green or accounted for.

## What keeps this honest

- `sites.test.mjs`: one site per brief, every log complete and ending in `done`, every database
  holding the gate outputs its log names and exactly the screens it keeps, the committed
  `JUDGMENT.md` equal to what the log renders to, the gallery equal to what it renders to.
- `judge.test.mjs`: the tool's own contract — verbatim gate capture, the screen walk that steps short
  of sticky headers, which screens a finished round keeps, the refusal rules.
- `scripts/build-pages.mjs` publishes each site's runtime files by name and its log's page and kept
  screenshots out of the log's database — never a directory walk, never the database itself — and
  `tests/pages-site.test.mjs` resolves every relative link on every published page.
- [`vlmkit.gates.json`](vlmkit.gates.json): integrity and contrast on the gallery and every demo page,
  served the Pages way by the intro page's server (its `webServer` starts it). The deploy workflow runs
  it before building the artifact; locally, `node dist/vlmkit.mjs gates run --config examples/sites/vlmkit.gates.json`.

## Adding a site

Write `briefs/<name>.md` in the shape of the others (what it is, layout and behaviour, visual
direction, required copy, states to show), give a fresh agent the protocol and the brief, then add a
`demoSite("<name>", [...runtime files])` line to `siteSections`, a page to `vlmkit.gates.json`, and
run `node examples/sites/gallery.mjs`. The gallery changed, so it gets a round in its own log too.
Re-run `judge.mjs <site> render` once the site is in `siteSections`: its `JUDGMENT.md` links into the
published page only from then.
